# Next major IPFS schema migration

This document describes the candidate contract after v5.2.0. The release number is assigned by semantic-release from a commit with a `BREAKING CHANGE` footer. Do not manually assign a version or treat the generated candidate files as released, pinned artifacts.

Every new required field needs a verified value before document generation or migration. A JSON patch must preserve unrelated `original_sale`, batch slices, existing audit/evidence references, and historical snapshot CIDs. Resolve a token's current metadata by its chain, contract, and token ID (NFT) or by chain and contract (ERC-20); a stored `ipfs_uri` still identifies the referenced snapshot.

## GasID result timestamp

The unreleased major candidate replaces required `data.prevented_emissions_calculation.calculated_at` with required `result_recorded_at`. The new value is the ISO 8601 time of the event that recorded the result for the same rule execution. It is not the arithmetic execution time, token issuance time, recycling time, audit completion time, or workflow finish time. The old key is rejected; no alias or optional fallback is included.

For each historical GasID, match the retained result `R` to its rule execution and use that execution's verified result event time. Preserve the result, unit, rule identity, audit reference, and historical snapshot CIDs. Records without an attributable result event remain blocked. Existing builders still emit `calculated_at` from issuance; they need a source-backed mapping before adoption. All compatibility evidence for the previous candidate predates this required-key change and must be rerun on the final head.

Shared network references use a positive integer `chain_id`; for NFT records on the currently supported Polygon/Amoy environments, it must agree with `network_name` and `environment.blockchain_network`. The schema does not prove a claimed chain/contract mapping on its own. Builders and migration gates must verify network and contract against deployed records; never derive chain ID from an address or a broad mainnet/testnet label.

`audit_data_hash` remains `hashObject(data)`: SHA-256 of canonicalized public `data`, not of the metadata envelope or private audit files. `schema.hash` remains SHA-256 of the canonicalized **published JSON Schema artifact**. The generator adds `items: false` to tuple nodes and cross-field credit-pair/network conditions before writing that artifact. Raw `toJSONSchema(schema)` therefore differs from the published artifact for Credit and all five NFT families. Current Smaug certificate producers hash the raw output, including GasID and RecycledID; those hashes do not identify this candidate artifact. Before adoption, every producer must use the exact released artifact hash (or reproduce the generator's normalization and conditions), and a corpus check must compare `schema.hash`, `schema.ipfs_uri`, pinned bytes and the released manifest. Existing historical hashes must remain historical.

The candidate does not add `Credit.data.methodologies`, `Methodology.data.credits`, `Collection.data.scope`, or `CreditRetirementReceipt.data.claim`.

## Consumer and release gates

1. Smaug builders generate every required field from a documented source and use the same Credit and Collection JSON URI wherever referenced. The existing 559 certificate and 94 receipt patches must pass the candidate schema without losing legacy fields. Extend the corpus gate to MassIDs/audits once the migration design is ready. A cached JSON count is not a token count.
2. Metadata Viewer validates and renders both new and historical versions, treats `ipfs_uri` as a cited snapshot, and labels live `tokenURI` navigation as current only after successful chain resolution. A stale CID fallback must be labeled as historical. Rivendell/Atlas must adopt the pinned release and preserve its own source-of-truth projections.
3. Run repository generation and full checks, independent review and CI on the final candidate head. Release/tag, all nine tagged JSON Schemas, hashes and pinned bytes require later readback before any Smaug package bump or production wave. This PR cannot authorize merge, release, pinning, deployment or transactions.

Generated JSON Schema enforces Credit slug/symbol pairs and supported NFT chain/network/environment agreement. Zod cross-field refinements such as trait equality, reference-chain equality and receipt totals are not fully represented there; authoritative generation and readback paths must run Zod as well as the published JSON Schema.

## Metadata revisions

All nine families share an optional root `revision`. First publications omit it; documents generated by the new update path must include it. Historical documents retain their original absence of a reason. Publication context belongs to the producer: schema validation cannot establish whether a predecessor exists or was fetched.

A revision preserves the exact nonempty `previous_uri` string, including legacy invalid pointers such as `ipfs://random-uri`; it is not a valid-IPFS-document primitive. Its overall `reason` is reused verbatim as the future token update event reason and compared at readback. `created_at` stays document generation time. No future transaction hash, execution timestamp, operator/signers, full history or copied old/new values belongs in the revision.

`comparison` is required. `verified` permits only changes actually derived from before/after documents and requires each change's `operation` (`add`, `replace`, `remove`). `unavailable` preserves declared explanations when the predecessor cannot be compared and prohibits operations entirely. Readers distinguish a producer's assertion from their own independent comparison; validation does not prove the assertion. A failed fetch does not make an update an initial publication.

Every change has a non-root RFC 6901 JSON Pointer `path`, individual `categories` and `reason`, with optional public `references` only when supporting evidence exists. Categories are `schema_migration`, `image_update`, `metadata_correction`, `reference_update`, `rollback`; multiple distinct categories may explain one field. Categories do not authorize scientific fact changes without separately approved provenance. Viewers derive category/path summaries from changes; do not add `change_types` or `changed_fields`.

Pointer tokens escape `~` as `~0` and `/` as `~1`. A removal path resolves in the predecessor; it need not resolve in the new document. The entire-document empty pointer and `/revision` subtree are excluded. Safe array comparison emits one replacement of the whole array at its member path, including reorders; do not assume positional item identity. Producers choosing index paths must verify actual array/index semantics from both documents, including no leading-zero array indices or `-` pseudo-element claims. Schema syntax alone cannot distinguish numeric object keys from array indices.

Limits: non-whitespace reasons with well-formed Unicode at most 500 UTF-16 units, predecessor/reference strings at most 4096, pointers at most 2048, 1–256 distinct change paths, 1–5 distinct categories per change, and 1–10 distinct references when supplied. These are validation failures, never truncation instructions. Supporting references use existing valid IPFS URI or HTTP(S) URL primitives; predecessor pointers intentionally do not. All objects reject extra fields. The token contract correction interface accepts at most 1500 UTF-8 bytes, sufficient for every well-formed 500-unit reason accepted by Zod. JSON Schema counts Unicode characters while Zod counts UTF-16 units, so astral characters require authoritative Zod validation. Zod remains required for path uniqueness and contextual checks not proven by generated JSON Schema.

The schemas package defines this interface; Smaug owns verified source comparison, reason provenance and mandatory update-path use. Initial/update, unknown predecessor, escaped keys, removals, arrays, retries/conflicts and lossless historical evidence remain part of the exact-candidate nine-family Smaug gate before this release.

## Methodology rules manifest provenance

New Methodology snapshots derive application rules from the same complete, immutable methodology-rules manifest used by the documentation. `data.rules_manifest` is required and records the full IPFS locator (including a file suffix), original-byte SHA-256, full source commit, and separate strict `framework` / `application` selectors with slug and version. Fetch and hash the received bytes; do not hash a regenerated or reformatted file. The producer verifies `sourceCommit`, manifest format, selected keys, versions and application membership before publication. Operational `data.version` remains separate from manifest format, framework, application and processor versions.

Each `mass_id_audit_rules` definition requires `application_rule_slug` for its exact source join, plus distinct, nonempty `implements_methodology_framework_rules` slugs in the selected framework. Preserve operational IDs, slugs, execution order and explicit legacy aliases. Preserve every normative association and its order; derive the application description from the selected application rule rather than choosing one normative description. Unknown links, conflicting selectors and mixed snapshots fail the producer gate; local shape validation cannot fetch or prove the referenced manifest.

The existing required `MassIDAudit.data.methodology.ipfs_uri` identifies the exact Methodology JSON used for the report. It supplies the manifest join without copying that manifest identity into every execution result. The producer must freeze and persist the Methodology snapshot at execution, then prove that every execution and its displayed definition belongs to that snapshot. `rule_source_code_url`, `rule_source_code_version` and `rule_processor_checksum` continue to identify the processor actually executed; the manifest commit must never replace them or be assumed equal to the processor commit.

The approved manifest description changes apply only to new snapshots. Preserve historical immutable documents, schema versions and execution provenance; missing historical source text is not filled from HEAD. A presentation revision does not claim that a new definition was executed in the past. Multiple-snapshot audit reports require a separate semantic decision.

New certificates freeze the latest successfully published audit reference at issuance. Existing certificate references remain unchanged. Shape validity cannot establish recency or successful publication; producer selection and post-publication readback must prove both.

Recompute schema artifacts and examples on the new candidate, and rerun the full nine-family real-producer and lossless-corpus gate against that exact schemas head and exact builder heads. Earlier candidate evidence does not release this gate. No schema change alone authorizes a package release, pin, deployment or production mutation.
